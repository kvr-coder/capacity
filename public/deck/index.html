01 · See  ·  VPM Dashboard

Where is the plant today, and who owns the gap?

The problem

  • Performance numbers live in separate spreadsheets and get compiled for meetings.
  • When a KPI misses, escalation is informal: it depends on who happens to hear.
  • Actions get agreed, then lost.

The approach

  • One board per topic (13 of them: safety, quality, production, supply chain, cost and more), each KPI shown against its target.
  • Four tiers, T1 to T4. Issues escalate up; cascade messages flow back down.
  • Actions with owners, due dates and status, in the same place.

What it is today

  • A working browser prototype with no server and no build step.
  • Layouts are editable, and day-by-day snapshots can be saved.
  • A public version runs on fully synthetic data.

02 · Capture  ·  Warehouse capture app

A warehouse of about 3,000 pallets, run on re-typing.

The problem

  • Label data (pallet ID, part, lot, expiry) is typed by hand into a shared spreadsheet.
  • One mistyped storage location and a pallet is effectively lost among thousands of bins.
  • Stock near expiry is noticed late, and nobody can cheaply check the floor matches the system.

The approach

  • Scan the barcode first (free and exact); read text from photos only as a fallback.
  • Nothing is guessed: every field passes a confirm screen before it is saved.
  • Works offline on the warehouse floor and syncs when connected.

Where it stands

  • Specified in detail across ten milestones, with the database, sync agent and approval flow in the repository.
  • Final ERP hookup needs a one-time on-site setup before it can run.
  • No measured results yet, so none are claimed.

03 · Decide  ·  Capacity Cockpit

Can five factories make what we have promised? If not, what fixes it?

The problem

  • A machine has a fixed number of hours; a plan asks for units. Whether they fit is rarely visible.
  • “We are at 90%” hides which machine is at 140% while another sits idle.
  • Machines and people run out differently, and the fixes cost different things.

The approach

  • Model every product's route through the machines, with separate machine and operator hours.
  • Name the real constraint on each machine: buy equipment, or hire people.
  • Try any change as an undoable “move” against a read-only baseline.

What it is today

  • Working, tested and publicly hosted. Runs entirely in the browser.
  • Generated data shaped like a real SAP extract, with an import path for the real thing.
  • Open it and try it: nothing to install.

  • Process order. Moulding on the left through to packing on the right; each ring is that machine's load.

03 · Decide  ·  A real finding

A plant-wide efficiency ramp first made things worse.

What happened. Ramping one plant's efficiency (OEE) to 98% raised utilisation and shortfall instead of lowering them.

Why. Seeded master data quietly outranked the planner's own scenario for 72 of 78 weeks, and the editor suggested a fixed 70% starting point.

The fix. A scenario move now always outranks background data, the start value is read from the real machine, and a deliberate decline is still allowed but labelled as one.

After the fix, same ramp to 98%
28 / 28machines reach the target (was 0)
−15.8%shortfall units
307 → 270overloaded machine-weeks
80.0 → 78.5%network utilisation

A test now fails if the problem ever returns.
